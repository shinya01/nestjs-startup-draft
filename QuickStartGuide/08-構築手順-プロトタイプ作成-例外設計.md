# 08-構築手順 - プロトタイプ作成 - 例外設計と実装

## 🎯 目的

アプリケーションで発生するあらゆるエラーを「業務例外（想定内）」と「システム例外（想定外）」に分類。
共通の `HttpExceptionFilter` を通じて、クライアントへ一貫した JSON レスポンスを返却する仕組みを構築します。

---

## 🧩 例外設計の基本方針

| 分類 | クラス名 | 用途 | ログレベル |
| :--- | :--- | :--- | :--- |
| **業務例外** | `BusinessException` | 在庫不足、重複登録、認証失敗など。独自の `code` を付与。 | `Warn` |
| **システム例外** | `SystemException` | DB接続失敗、外部APIタイムアウト、予期せぬコードバグ。 | `Error` |

---

## 🧾 共通エラー構造の定義

すべてのエラーレスポンスを以下の形式に統一します。

```ts
// src/common/swagger/error-response.dto.ts
export class ErrorResponseDto {
  @ApiProperty({ example: false }) success: boolean;
  @ApiProperty({ example: 400 }) statusCode: number;
  @ApiProperty({ example: '2026-01-27T22:00:00Z' }) timestamp: string;
  @ApiProperty({ example: '/users' }) path: string;
  @ApiProperty({ example: '入力内容に誤りがあります' }) message: string;
  @ApiProperty({ example: 'ALREADY_EXISTS', required: false }) code?: string;
  @ApiProperty({ example: 'BadRequestException' }) error: string;
}
```

## 🛠️ グローバル例外フィルターの実装

このフィルターが、NestJS 内のあらゆる場所から投げられた例外をキャッチし、整形します。

```ts
// src/common/filters/http-exception.filter.ts
@Catch()
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();
    const request = ctx.getRequest<Request>();

    const status = exception instanceof HttpException 
      ? exception.getStatus() 
      : HttpStatus.INTERNAL_SERVER_ERROR;

    // 業務エラー特有のコードを取得
    const code = exception instanceof BusinessException ? exception.code : undefined;
    const message = this.extractMessage(exception);

    const responseBody = {
      success: false,
      statusCode: status,
      timestamp: new Date().toISOString(),
      path: request.url,
      message,
      error: exception instanceof HttpException ? exception.name : 'InternalServerError',
      ...(code && { code }),
    };

    // ログ出力（Pinoを通じて構造化ログとして出力）
    if (status >= 500) {
      logger.error({ exception, path: request.url }, 'System Error');
    } else {
      logger.warn({ code, message, path: request.url }, 'Business Error');
    }

    response.status(status).json(responseBody);
  }
  // ... extractMessage 実装 (バリデーションエラーの配列平坦化など)
}
```

## 🎨 Swagger 用カスタムデコレーター

コントローラーの記述をスッキリさせるため、よく使うエラーレスポンスをまとめます。

```ts
// src/common/decorators/api-error-response.decorator.ts
export function ApiErrorResponses() {
  return applyDecorators(
    ApiResponse({ status: 400, type: ErrorResponseDto, description: 'Bad Request / Business Error' }),
    ApiResponse({ status: 404, type: ErrorResponseDto, description: 'Not Found' }),
    ApiResponse({ status: 500, type: ErrorResponseDto, description: 'Internal Server Error' }),
  );
}
```

## 🚀 アプリケーションへの適用 (main.ts)

```ts
// src/main.ts
async function bootstrap() {
  const app = await NestFactory.create(AppModule, { bufferLogs: true });
  
  // グローバルフィルターの登録
  app.useGlobalFilters(new HttpExceptionFilter());

  // Swagger 設定
  const document = SwaggerModule.createDocument(app, config, {
    extraModels: [ErrorResponseDto], // デコレーターで使用するモデルを登録
  });
  // ...
}
```

## 💡 使用例

```ts
// service
if (exists) {
  throw new BusinessException(BusinessErrorCodes.ALREADY_EXISTS, 'このメールは既に使われています');
}

// controller
@ApiTags('Users')
@Controller('users')
@ApiErrorResponses() // これだけで400, 404, 500のドキュメントが生成される
export class UserController { ... }
```

## ✅ 補足ポイント

- **デバッグのしやすさ**: ログ出力時に `cause` を含めることで、スタックトレースを保持したまま抽象化されたエラーを投げることができます。
- **フロントエンドの対応**: `code` を見るだけで「どのメッセージを出すべきか」をフロントエンド側で判断可能になります。
- **バリデーション統合**: `class-validator` によるエラーもこのフィルターを通過するため、メッセージ形式がバラバラになりません。
